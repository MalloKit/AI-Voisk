## 1. 한 줄 요약

음성 주문과 상황 기반 메뉴 추천이 내장된 태블릿 키오스크. 고객은 "말로야 주문"이라고 부른 뒤 주문하거나 "해장에 좋은 거 추천해줘"처럼 상황만 말하면 되고, 점주는 웹 관리자 대시보드에서 메뉴·가격·추천 정책을 관리한다.

---

## 2. 배경과 문제

| 구분 | 내용 |
|---|---|
| 고객 문제 (공통) | 메뉴가 카테고리 여러 단에 흩어져 있어 원하는 메뉴를 찾기 위해 화면을 오가며 탭을 반복해야 함 |
| 고객 문제 (일반) | 메뉴가 많은 매장에서 "뭘 먹을지" 고르는 데 시간이 오래 걸림. 기존 키오스크는 상황에 맞는 추천을 해주지 못함 |
| 고객 문제 (시니어) | 터치 조작 자체가 어려워 주문을 포기하거나 뒷사람 눈치를 봄 |
| 매장 문제 | 직원이 하던 메뉴 추천·추가 권유가 키오스크 전환 후 사라져 객단가와 이익률 관리가 어려움. 메뉴·가격 변경도 번거로움 |
| 제도 환경 | 장애인차별금지법 개정으로 무인정보단말기 접근성 편의 제공 의무가 2026년 1월부터 기존 설치 기기까지 적용. 음성 안내·조작 기능 수요 증가 |

## 3. 대상 사용자

| 사용자 | 핵심 니즈 | 보이스크가 주는 가치 |
|---|---|---|
| 일반 고객 | 빠르게 고르고 싶음, 뭘 먹을지 모르겠음 | 상황 기반 추천, 한 문장 주문 |
| 시니어·디지털 취약 고객 | 터치 없이 주문하고 싶음 | 음성 주문, 느린 안내, 되묻기 |
| 매장 관리자(점주) | 메뉴·가격을 쉽게 관리, 이익 높은 메뉴 판매 확대 | 웹 대시보드, 이익 기준 추천 순서 설정, 주문·추천 성과 확인 |

## 4. 목표와 범위

### 캡스톤 범위 (이번 학기)
- 갤럭시 탭 기반 AI 보이스크 키오스크 앱 (터치 주문 + 음성 주문 + 추천 일체형)
- "말로야 주문" 호출어, 음성 주문, 상황 기반 메뉴 추천
- 서버 (API · DB) 구축
- 웹 관리자 대시보드: 메뉴 추가·삭제·가격 변경, 원가율·추천 정책, 주문 내역·추천 성과
- 태블릿 ↔ 서버 데이터 동기화 (메뉴 내려받기, 주문 올려보내기)
- 3D 프린팅 키오스크 케이스로 실물 시연

### 범위 밖 (이후 단계)
- 기존(타사) 키오스크에 음성 기능을 얹는 애드온 방식
- 실제 결제 처리 (시연에서는 모의 결제)
- 다매장 운영 (데이터 구조만 매장 단위로 확장 가능하게 설계)
- POS·주방 디스플레이 연동
- 윈도우 키오스크 대응, 접근성 인증, B2B 영업

## 5. 사용자 시나리오

### 시나리오 A — 일반 고객, 상황 기반 추천
1. "말로야 주문" → 화면에 듣는 중 표시와 함께 "네, 말씀하세요"
2. "어제 술 먹었는데 해장에 좋은 메뉴 추천해줘"
3. 해장 태그 메뉴 중 관리자 정책에 따라 상위 3개를 추천 카드로 띄우고 1순위를 말로 소개
   "속 풀기엔 순두부찌개 어떠세요? 콩나물국밥, 북엇국도 있어요."
4. "콩나물국밥으로 줘" → 확인 후 장바구니에 담기 (담기는 모습을 화면에 표시)
5. (관리자 설정 시) "음료도 같이 하시겠어요?" 추가 제안 1회

### 시나리오 B — 일반 고객, 바로 주문
1. "말로야 주문" → "제육덮밥 두 개랑 콜라 하나"
2. 요약 확인 → 장바구니 반영 → 결제 안내

### 시나리오 C — 시니어 고객, 음성 주문
1. 화면의 "말로 주문하기" 버튼을 누르거나 "말로야 주문"이라고 부름 → 시니어 모드 선택
2. "된장찌개 하나 줘요" → 느린 속도로 확인, 필요한 옵션만 되묻기
3. 장바구니 반영 → 카드 투입 위치를 음성으로 안내

### 시나리오 D — 고객, 터치와 음성 혼용
1. 터치로 메뉴를 둘러보다가 "말로야 주문, 이거 두 개로 바꿔줘"
2. 현재 화면 맥락(보고 있는 메뉴, 장바구니)을 반영해 처리

### 시나리오 E — 관리자, 메뉴·가격 변경
1. 관리자가 PC나 휴대폰 브라우저로 대시보드 로그인
2. 신메뉴 "얼큰 순두부" 추가 (가격·카테고리·사진·옵션·원가율 입력)
3. 서버가 메뉴 설명을 바탕으로 상황 태그와 추천용 데이터를 자동 생성 → 관리자가 태그 확인
4. 김치찌개 가격 9,000원 → 9,500원 변경, 비빔밥 품절 처리
5. 저장 즉시 매장 태블릿에 반영 (진행 중인 주문이 있으면 주문 완료 후 반영)

### 시나리오 F — 관리자, 성과 확인
1. 대시보드에서 오늘 주문 수, 음성 주문 비율, 추천 메뉴 선택률, 추천 경유 매출 확인
2. 추천 정책 슬라이더를 "매장 이익 우선" 쪽으로 조정 → 태블릿에 즉시 반영

## 6. 주요 기능

### 고객용 (태블릿 키오스크)
| 기능 | 설명 |
|---|---|
| 터치 주문 | 일반 키오스크와 동일한 카테고리·메뉴·옵션·장바구니 화면 |
| 호출어 "말로야 주문" | 대기 중 호출어를 감지하면 음성 주문 시작. 화면 버튼으로도 시작 가능 |
| 자연어 음성 주문 | 정확한 메뉴명이 아니어도 인식 ("짜장", "아아", "그 매운 거") |
| 상황 기반 메뉴 추천 | 해장·다이어트·든든하게·가볍게·매운 거·아이랑 등 상황과 취향을 말하면 맞는 메뉴 추천 |
| 추천 이유 안내 | "국물이 있어 속 풀기 좋아요"처럼 짧은 근거 제시 |
| 화면 연동 피드백 | 음성으로 처리한 내용을 화면에 그대로 보여줌 (해당 메뉴 강조, 장바구니 담기 표시) |
| 옵션 확인 대화 | 온도·사이즈·수량 등 필수 옵션만 되묻기 |
| 주문 확인·정정 | 담기 전 요약 확인, "하나 빼줘", "이거 두 개로" 같은 정정 처리 |
| 사용자 모드 | 일반 모드(짧은 응답) / 시니어 모드(느린 음성, 큰 글씨, 되묻기 강화) |
| 오프라인 동작 | 서버 연결이 끊겨도 마지막으로 받은 메뉴로 주문 가능, 주문은 연결 복구 후 전송 |

### 관리자 대시보드 (웹)
| 메뉴 | 기능 |
|---|---|
| 메뉴 관리 | 메뉴 추가·수정·삭제, 가격 변경, 사진 업로드, 옵션(온도·사이즈) 설정, 품절 처리, 노출 순서 |
| 카테고리 관리 | 카테고리 추가·삭제·순서 변경 |
| 원가·추천 | 메뉴별 원가율 입력, 추천 정책 슬라이더(고객 적합 ↔ 매장 이익), 추천 제외 메뉴, 매장 우선 메뉴 |
| 태그·동의어 | 상황 태그 자동 제안 확인·수정, 메뉴별 동의어 등록 ("아아" → 아이스 아메리카노) |
| 음성 설정 | 호출어 감도, 안내 음성 속도, 추가 제안 사용 여부, 기본 사용자 모드 |
| 주문 내역 | 기간별 주문 목록, 음성 주문 / 터치 주문 구분 |
| 통계 | 주문 수, 음성 주문 비율, 추천 노출·선택률, 추천 경유 매출, 인기 메뉴 |
| 기기 관리 | 등록된 태블릿 목록, 온라인 상태, 마지막 동기화 시각, 메뉴 버전 |

## 7. 호출어 설계

### 동작 방식
```
[호출어 대기] ─ "말로야 주문" 감지 ─→ [청취] → 주문 대화 → 주문 완료
      ↑                                                     │
      └──────────── 무음 8초 또는 주문 완료 ────────────────┘
```
- 대기 중에는 경량 호출어 감지 모델만 동작하고, STT는 호출어 감지 후에만 켠다
- 대기 중 음성은 메모리 순환 버퍼(1~2초)에만 두고 즉시 덮어쓴다. 디스크 저장·네트워크 전송 없음
- 화면 버튼 "말로 주문하기"를 항상 병행 (시끄러운 매장, 시니어 고객 대비)

### 기술 선택
| 항목 | 선택 | 비고 |
|---|---|---|
| 호출어 엔진 (캡스톤) | Porcupine (Picovoice) | 한국어 지원, 안드로이드 SDK, 콘솔에서 커스텀 호출어 생성 |
| 호출어 엔진 (이후) | sherpa-onnx KWS 자체 학습 검토 | STT와 스택 통일, 라이선스 비용 제거 |
| 마이크 상시 사용 | 안드로이드 포그라운드 서비스 (microphone 타입) | 키오스크 앱이 항상 화면에 떠 있으므로 시작 제약 없음 |
| 기기 설정 | 빅스비 호출어 끄기, 배터리 최적화 제외 | 마이크 충돌·서비스 종료 방지 |

### 프라이버시 원칙
- 오디오 데이터는 음성 엔진(Kotlin) 안에서만 처리되고, 앱의 다른 부분(Dart)에는 인식된 텍스트만 전달한다
- 앱 어디에도 오디오를 파일로 저장하거나 서버로 보내는 코드를 두지 않는다
- 서버로는 의도·선택 메뉴 같은 구조화 데이터만 보내고, 고객 발화 원문은 보내지 않는다
- 키오스크에 "호출어 이후 음성만 처리하며 저장하지 않습니다" 안내 표시, 화면에 대기 중 / 듣는 중 상태 아이콘 구분
- 정확도 측정용 녹음은 동의한 참가자 대상 테스트 빌드에서만 수행, 운영 빌드에서는 녹음 기능 제외

## 8. 추천 로직

### 처리 흐름
```
발화 → 의도 분류 ─┬─ 주문 → 메뉴 매칭 → 확인
                  └─ 추천 요청 → 상황·취향 추출
                                     ↓
                     후보 필터 (품절·추천 제외·옵션 조건)
                                     ↓
                     적합도 계산 (발화 ↔ 메뉴 태그·설명)
                                     ↓
                     적합도 기준선 미달 메뉴 제외
                                     ↓
                     최종 점수 = 적합도 × w1 + 이익 점수 × w2 + 매장 우선 × w3
                                     ↓
                     상위 3개 추천 카드 표시 + 1순위 음성 소개
```

### 점수 구성
| 항목 | 산출 방식 |
|---|---|
| 적합도 | 발화에서 뽑은 상황·취향과 메뉴 태그·설명의 임베딩 유사도 |
| 이익 점수 | 원가율이 낮을수록 높게 (매장 내 메뉴끼리 정규화) |
| 매장 우선 | 신메뉴·재고 소진 대상 등 관리자가 지정한 가산점 |
| 가중치 w1, w2, w3 | 대시보드 추천 정책 슬라이더로 결정, 서버 동기화로 태블릿에 반영 |

### 원칙
- 이익 점수는 "적합한 메뉴들 사이의 순서"를 바꾸는 데만 쓴다. 적합도 기준선을 넘지 못한 메뉴는 이익이 높아도 추천하지 않는다
- 고객이 메뉴를 직접 말하면 추천 로직을 거치지 않고 그대로 주문한다
- 추가 제안은 주문당 1회까지만 한다 (시니어 모드에서는 기본 꺼짐)

### 메뉴 추천 데이터 준비
- 대시보드에서 메뉴를 등록·수정하면 서버가 상황 태그 자동 제안과 메뉴 임베딩 계산을 수행
- 관리자는 제안된 태그를 확인·수정
- 태블릿은 계산이 끝난 태그·임베딩을 메뉴 데이터와 함께 내려받아 저장 → 런타임 추천은 전부 기기 안에서 처리

## 9. 시스템 구성

```
┌──────────── 관리자 ────────────┐
│  웹 관리자 대시보드 (브라우저)    │
└───────────────┬────────────────┘
                │ HTTPS (관리자 로그인)
┌───────────────▼────────────────┐
│  서버 (Oracle Cloud)            │
│  API · DB · 이미지 저장          │
│  태그 제안 · 메뉴 임베딩 계산     │
└───────────────┬────────────────┘
                │ HTTPS + 실시간 알림 (기기 토큰)
                │ ↓ 메뉴·가격·정책  ↑ 주문·추천 로그
┌───────────────▼──────── 갤럭시 탭 · AI 보이스크 앱 ────────────┐
│  화면 (Flutter) : 터치 주문 화면 · 추천 카드 · 음성 상태 표시     │
│  도메인 (Dart)  : 대화 상태 기계 · 주문 명령 · 추천 엔진          │
│  데이터 (Dart)  : 로컬 DB(메뉴 캐시) · 동기화 · 주문 전송 대기열   │

│  음성 엔진 (Kotlin) : 마이크 · 호출어 · STT · NLU·임베딩 추론 · TTS │
└──────────────────────────────────────────────────────────────┘
```

## 10. 데이터 동기화 설계

### 원칙
- 메뉴·가격·정책의 기준은 서버, 진행 중인 주문의 기준은 태블릿
- 태블릿은 오프라인 우선: 서버 연결 없이도 마지막으로 받은 메뉴로 주문을 받는다

### 흐름
| 방향 | 데이터 | 방식 |
|---|---|---|
| 서버 → 태블릿 | 메뉴, 카테고리, 가격, 옵션, 품절, 태그·임베딩, 추천 정책, 음성 설정 | 변경 시 서버가 실시간 알림(WebSocket) → 태블릿이 변경분만 요청(메뉴 버전 번호 기준) |
| 서버 → 태블릿 | 메뉴 사진 | 변경된 사진만 내려받아 기기에 저장 |
| 태블릿 → 서버 | 주문, 추천 노출·선택 로그, 기기 상태 | 주문 전송 대기열에 쌓고 순서대로 전송, 실패 시 재시도 |

### 세부 규칙
- 메뉴 버전 번호: 서버에서 메뉴가 바뀔 때마다 증가, 태블릿은 자기 버전 이후 변경분만 받음
- 주문 중 가격 변경: 진행 중인 주문은 시작 시점 메뉴 기준으로 끝내고, 주문 완료 후 새 버전 적용
- 중복 주문 방지: 태블릿이 주문마다 고유 ID를 만들어 보내고, 서버는 같은 ID를 한 번만 저장
- 재연결: 연결 복구 시 미전송 주문 전송 → 최신 메뉴 버전 확인 순서

### 주요 API (개략)
| 구분 | 엔드포인트 예 | 용도 |
|---|---|---|
| 관리자 | 로그인, 메뉴·카테고리·옵션 CRUD, 사진 업로드, 원가·정책·음성 설정 수정 | 대시보드 |
| 관리자 | 주문 조회, 통계 조회, 기기 목록 | 대시보드 |
| 기기 | 기기 등록, 메뉴 변경분 조회, 정책·설정 조회 | 태블릿 동기화 |
| 기기 | 주문 업로드, 로그 업로드, 상태 보고 | 태블릿 → 서버 |
| 실시간 | 변경 알림 채널 | 서버 → 태블릿 |

### 주요 데이터 모델 (개략)
| 모델 | 주요 항목 |
|---|---|
| 매장 | 매장명, 추천 정책 가중치, 음성 설정 (다매장 확장 대비) |
| 카테고리 | 이름, 순서 |
| 메뉴 | 이름, 가격, 카테고리, 사진, 설명, 원가율, 품절, 추천 제외, 매장 우선, 노출 순서 |
| 옵션 | 옵션 그룹(온도·사이즈), 선택지, 추가 금액 |
| 태그·동의어 | 메뉴별 상황 태그, 동의어, 임베딩 |
| 기기 | 기기 ID, 토큰, 마지막 동기화, 메뉴 버전 |
| 주문 | 주문 ID, 기기, 품목·옵션·수량, 금액, 주문 방식(음성/터치), 추천 경유 여부 |
| 추천 로그 | 노출 메뉴, 선택 메뉴, 적용 정책 |

## 12. 설계 원칙과 디자인 패턴

### 설계 원칙
- 음성과 터치는 같은 주문 명령을 거친다: 어떤 경로로 들어와도 장바구니는 한 곳에서 바뀐다
- 오디오는 음성 엔진 밖으로 나가지 않는다: Dart 쪽과 서버에는 텍스트·구조화 데이터만 전달
- 서버는 메뉴의 기준, 태블릿은 오프라인에서도 주문을 받는다
- AI는 "입력 해석과 적합도 판단"에만 쓰고, 순위 결정·주문 처리는 결정론적 로직으로 처리한다
- 매장 이익은 적합한 후보 안에서만 반영한다

### 패턴 적용 위치
| 패턴 | 적용 위치 | 목적 |
|---|---|---|
| Command | 주문 조작 | 메뉴 담기·빼기·수량 변경·옵션 선택을 명령 객체로 통일. 터치와 음성이 같은 명령을 사용하고, 실행 취소·로그 처리 |
| State | 대화 관리 | 호출어 대기 → 청취 → 이해 → 추천/확인 → 실행 → 결제 안내. 상태별 허용 발화와 다음 행동 분리 |
| Strategy | 추천 정책, 호출어·STT 엔진 | 추천 정책(적합 우선 / 균형 / 이익 우선)과 호출어 엔진(Porcupine / sherpa-onnx)을 교체 가능하게 |
| Pipeline (Filter) | 추천 엔진 | 후보 필터 → 적합도 → 기준선 컷 → 점수 합산 → 정렬을 단계별 독립 모듈로 구성 |
| Chain of Responsibility | 메뉴 매칭 | 동의어 사전 → 퍼지 매칭 → 임베딩 매칭 순으로 실패 시 다음 단계로 위임 |
| Facade | 음성 엔진 | 호출어·STT·NLU·TTS를 하나의 VoiceEngine 인터페이스로 묶어 Dart 쪽이 모델 세부를 모르게 함 |
| Adapter | 플랫폼 채널 경계 | Kotlin 음성 엔진 이벤트를 Dart 도메인 이벤트로 변환 |
| Observer | 음성 이벤트, 서버 변경 반영 | 음성 엔진 이벤트(호출어 감지, 인식 결과)를 스트림으로 구독, 서버 변경 알림 수신 시 로컬 데이터 갱신 |
| Repository (오프라인 우선) | 메뉴 데이터 | 화면과 도메인은 로컬 DB만 읽고, 동기화 모듈이 서버 변경분을 로컬 DB에 반영 |
| Outbox | 주문 전송 | 주문을 로컬 대기열에 먼저 저장하고 순서대로 서버 전송, 실패 시 재시도. 주문 유실 방지 |
| Idempotency Key | 주문 업로드 API | 주문 고유 ID로 재전송 시 중복 저장 방지 |
| Layered (Router-Service-Repository) | 서버 | API 라우터, 비즈니스 로직, DB 접근 분리 |
| DTO | 서버 ↔ 클라이언트 | API 요청·응답 형식을 DB 모델과 분리, packages/shared에서 공유 |
| MVVM | 키오스크 앱·대시보드 (Flutter) | 화면과 상태(Riverpod) 분리 |

## 15. 검증 계획

- 호출어: 팀원·지인 다수 화자의 "말로야 주문" 녹음으로 감지율 측정, 매장 소음·일상 대화 음원을 수 시간 재생해 오작동 횟수 측정
- 음성 인식·의도: 합성 + 실녹음 발화 세트로 의도 분류·인식 정확도 측정
- 추천: 상황 질의 세트를 팀원·지인이 적합 여부 판정해 추천 적합률 측정, 추천 정책별(적합 우선 / 균형 / 이익 우선) 결과 비교
- 동기화: 대시보드 변경 → 태블릿 반영 시간 측정, 와이파이 차단 상태에서 주문 후 복구 시 전송 확인
- 사용성: 같은 주문 과제를 터치 주문 / 음성 주문으로 각각 수행해 탭 수·소요 시간 비교 (일반·시니어 각각)
