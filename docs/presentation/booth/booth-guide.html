부스 준비와 5분 흐름

관람객은 지나가다 멈춥니다. 첫 30초에 "직접 말해 보는 키오스크"라는 걸 보여 주고, 관심을 보이면 5분 대본으로 이어 갑니다.

부스 배치

  • 태블릿(키오스크 앱): 관람객 정면. 직접 말해 보게 하는 주인공.
  • 노트북: 서버와 점주 웹. 추천 정책 슬라이더를 보여 줄 때 돌려서 보여 줌.
  • 모니터: 소개 영상(brag.mp4, 1분 44초) 무한 반복. 소리를 꺼도 자막이 나옴.
  • 발표 덱(index.html)은 질문이 깊어질 때 시스템 구성·평가 장을 띄우는 용도.

시작 전 확인

  • 노트북 서버(start-demo.bat) 켜짐, 태블릿과 같은 Wi-Fi. 안 붙으면 start-demo-tunnel.bat.
  • 서버의 Claude API 키가 들어 있는지(없으면 음성 주문 대신 터치 안내가 뜸).
  • 태블릿 빅스비 호출 꺼짐, 미디어 볼륨 충분히.
  • 장바구니 비우고 처음 화면에서 시작. 시연 주문은 시연 결제로만.
  • 부스가 시끄러우면 태블릿 가까이에서 또박또박 말하도록 안내.

말하는 요령

  • 대본은 외우지 말고 굵은 글씨(핵심 문장)만 기억합니다.
  • 시연은 말보다 먼저 합니다. 보여 주고, 그다음 설명합니다.
  • 관람객이 직접 말해 보게 하면 대본 2·3번은 줄여도 됩니다.
  • 모르는 질문은 짐작해서 답하지 않고 "확인해서 알려 드리겠다"고 합니다.
  • 숫자를 말할 때는 범위도 같이 말합니다(예: 합성 발화 67개 기준).
  • 교수님·심사위원에게는 4번 질문 중 기술·평가 묶음을 먼저 준비합니다.

45초

노트북: 점주 웹 'AI 추천·음성' 화면

이 키오스크는 점주가 관리합니다. 메뉴, 사진, 품절을 여기서 바꾸면 매장 태블릿에 바로 반영됩니다.

재미있는 건 추천 정책입니다. 슬라이더를 '고객 적합 우선'에서 '매장 이익 우선'으로 옮기면, 저희 평가에서 추천 1순위 메뉴의 평균 원가율이 31.6%에서 23.5%로 내려갔습니다. 그래도 상황에 맞는 메뉴를 추천한 비율은 100% 그대로였습니다. 상황에 안 맞는 메뉴는 이익이 커도 추천하지 않도록 기준선을 뒀기 때문입니다.

통계 화면에서는 음성으로 주문한 비율, 추천 메뉴를 골라 간 비율, 추천으로 생긴 매출까지 볼 수 있고, 손님이 키오스크에서 직원 호출을 누르면 여기로 바로 알림이 옵니다.

필요하면 덱 7장(시스템 구성)

안에서는 이렇게 움직입니다. 태블릿이 목소리를 글자로 바꾸고, 저희 서버는 그 글자만 받아서 Claude Haiku라는 AI에게 "무슨 메뉴를 몇 개 주문한 건지", "이 상황에 어떤 메뉴가 맞는지"를 묻습니다. 대신 추천 순위는 AI가 아니라 정해진 규칙이 정합니다. AI가 매장에 없는 메뉴를 말해도 서버가 매장 메뉴와 다시 대조해서 걸러 냅니다.

음성 인식이 메뉴 이름을 다른 낱말로 받아 적을 때도 있습니다. "식혜"를 "시계"로 적는 식인데, 서버가 발음을 비교해 비슷한 메뉴를 찾고 손님께 한 번 더 확인합니다.

마이크는 버튼을 누른 동안만 켜지고, 목소리를 녹음하거나 저장하지 않습니다. 서버가 꺼지거나 인터넷이 끊기면 터치 주문으로 안내하고, 주문은 기기에 모아 뒀다가 연결되면 순서대로 보냅니다.

30초 버전과 시연이 막혔을 때

지나가는 관람객에게 30초

"말로 주문하는 키오스크예요. 버튼을 누르고 '제육 두 개랑 콜라 하나'라고 말하면 한 번에 담기고, '해장할 만한 거'처럼 상황만 말해도 매장 메뉴 중 세 가지를 이유와 함께 추천해 줍니다. 마이크는 버튼을 누른 동안만 켜지고 녹음하지 않아요. 한번 말해 보시겠어요?"

교수님·심사위원에게 1분 (기술 중심)

"태블릿 안드로이드 음성 인식으로 문장을 받고, FastAPI 서버가 매장 메뉴·동의어·옵션·장바구니와 함께 Claude Haiku에 구조화 출력(JSON 스키마)으로 의도를 물어 다시 메뉴와 대조합니다. 추천은 Haiku가 상황 적합도와 이유만 내고, 순위는 키오스크 추천 엔진이 점주 정책 가중치로 정합니다. 합성 발화 67개 평가에서 의도·품목·옵션·추천 적합률 100%, 정책을 이익 쪽으로 옮기면 1순위 평균 원가율 31.6%에서 23.5%로 내려가면서 적합률은 유지됐습니다. 응답 시간 4.06초는 목표 2초에 못 미쳐 실제 API 경로로 다시 측정할 예정입니다."

시연이 막혔을 때

상황이렇게 말하고, 이렇게 합니다
말을 못 알아들음"부스가 시끄러워서 그래요. 가까이서 한 번 더 해 볼게요." 태블릿에 가까이 대고 짧게 다시 말합니다. 키오스크도 못 알아들으면 다시 묻도록 만들어져 있습니다.
"화면을 눌러 주문해 주세요"가 뜸서버나 AI 연결이 끊긴 상태입니다. "연결이 끊기면 이렇게 터치 주문으로 넘어가도록 만들었어요"라고 오히려 기능으로 설명하고, 터치로 주문을 이어 갑니다. 그 사이 노트북 서버 창과 Wi-Fi를 확인합니다.
응답이 느림"지금 AI에게 메뉴를 물어보는 중이에요. 이 시간을 2초로 줄이는 게 저희 다음 과제입니다." 기다리는 동안 음성 패널의 안내 문구를 가리킵니다.
태블릿이 아예 안 됨모니터의 소개 영상을 처음부터 보여 주며 같은 순서로 설명합니다. 영상에 시연 장면이 모두 들어 있습니다.
엉뚱한 메뉴가 담기려 함담기 전 확인 질문이 나오므로 "아니요"라고 답하고, "그래서 담기 전에 꼭 한 번 확인하도록 했어요"라고 설명합니다.

예상 질문과 답

굵은 첫 문장으로 먼저 답하고, 더 물으면 뒤 내용을 덧붙입니다. 표시된 출처는 저장소 기준입니다.

처음 보는 관람객
Q1
그냥 키오스크에 음성 기능만 붙인 거 아닌가요?
말을 알아듣는 것에 더해, 상황을 듣고 메뉴를 골라 주는 게 핵심입니다. "해장할 만한 거"처럼 메뉴 이름이 없는 말에도 매장 메뉴 중 세 가지를 이유와 함께 추천하고, 그 순위는 점주가 정한 정책을 따릅니다.
Q2
계속 듣고 있는 건가요? 제 말이 녹음되나요?
아니요. 화면의 '말로 주문하기' 버튼을 누른 동안만 마이크가 켜집니다. 호출어로 부르는 기능은 일부러 뺐습니다. 목소리를 녹음하거나 저장하지 않고, 서버에는 인식된 글자만 가며 그 글자도 저장하거나 로그에 남기지 않습니다. 화면에도 이 안내가 늘 떠 있습니다.
Q3
사투리나 어르신 발음도 알아듣나요?
인식은 안드로이드 기본 음성 인식기를 쓰고, 잘못 받아 적은 메뉴는 발음으로 다시 찾습니다. 예를 들어 "식혜"를 "시계"로 받아 적어도 발음이 비슷한 메뉴를 찾아 확인합니다. 오인식 문장 34개와 무관한 말 6개로 3번 재 보니 맞힌 비율이 80%에서 95%로 올랐고, 무관한 말을 메뉴로 담은 경우는 없었습니다. 다만 실제 어르신 사용자 테스트는 아직 남은 과제입니다.출처: 커밋 e0bc9fd
Q4
시끄러운 식당에서도 되나요?
아직 실제 매장 소음에서 검증하지는 못했습니다. 못 알아들으면 다시 묻고, 반복해서 실패하면 터치 주문이나 직원 호출로 안내합니다. 실제 갤럭시 탭 마이크로 하는 검증이 다음 단계입니다.
Q5
외국인도 쓸 수 있나요?
화면은 한국어, 일본어, 영어, 중국어 4개 언어로 바꿀 수 있고, 음성 주문은 지금 한국어만 됩니다.
Q6
말이 서툴면 어떡하죠? 결국 터치를 해야 하나요?
말과 터치를 섞어 써도 됩니다. 같은 장바구니를 쓰기 때문에 말로 담고 터치로 빼도 되고, 맵기 같은 선택지는 화면 버튼으로도 고를 수 있습니다. 큰 글씨·느린 음성의 "크게·천천히" 모드도 있습니다.
Q7
AI가 엉뚱한 메뉴를 담으면요?
담기 전에 반드시 "담을까요?"라고 확인하고, 서버가 AI의 답을 매장 메뉴와 다시 대조합니다. 매장에 없는 메뉴는 담기지 않고, 근거가 없으면 되묻습니다.
기술
Q8
어떤 기술로 만들었나요?
키오스크는 Flutter 안드로이드 앱, 서버는 FastAPI, 점주·회사 관리자 웹은 React, DB는 Azure MySQL입니다. 음성 인식·음성 안내는 Kotlin으로 만든 플러그인이 안드로이드 내장 SpeechRecognizer와 TextToSpeech를 씁니다. AI는 Claude Haiku(claude-haiku-5-5)를 서버에서 호출합니다.
Q9
AI는 정확히 무슨 일을 하나요?
두 가지만 합니다. 손님 말에서 주문 의도(메뉴·수량·옵션)를 뽑는 것, 상황에 맞는 정도(0~100)와 추천 이유를 내는 것입니다. 추천 순위, 옵션 되묻기, 장바구니 변경은 정해진 규칙과 코드가 합니다. 답은 JSON 스키마로 받는 구조화 출력이라 형식이 흔들리지 않습니다.
Q10
추천 순위는 어떻게 정하나요?
네 단계입니다. 품절·추천 제외 메뉴를 거르고, AI가 상황 적합도를 매기고, 기준선에 못 미치는 메뉴를 빼고, 남은 메뉴를 "적합도 × w1 + 이익 점수 × w2 + 매장 우선 × w3"로 점수 매겨 상위 3개를 고릅니다. 가중치는 점주의 정책 설정에서 나옵니다. 맞는 메뉴가 없으면 최근 30일 인기 메뉴를 보여 주고 되묻습니다.
Q11
왜 기기 안에서 돌리는 AI가 아니라 서버 AI를 썼나요?
학습 데이터 없이도 정정·상황 추천 품질을 확보하려고 서버에서 Claude Haiku를 호출하는 쪽을 택했습니다. 처음 구상은 기기 안 추론(ONNX)이었는데, 바꾼 이유와 대가(응답 시간, 인터넷 필요)를 설계 문서에 남겼습니다. 대신 "네", "아니요", "결제할게요" 같은 짧은 대답은 서버를 거치지 않고 기기가 바로 처리합니다.출처: docs/AI_VOICE_DESIGN.md 2장
Q12
응답이 느린데, 2초 목표는 어떻게 맞추나요?
평가 때 평균 4.06초(상위 10%는 6.94초)로 목표 2초에 못 미쳤습니다. 이 값은 평가를 Claude Code 구독의 명령줄 도구를 거쳐 돌려서 실행 비용이 더해진 값이라, 실제 API 키 경로로 다시 재야 합니다. 그 결과를 보고 줄일 방법을 정합니다. 지금은 숨기지 않고 남은 과제로 발표합니다.출처: ml/voice_eval/REPORT.md
Q13
인터넷이나 서버가 끊기면요?
터치 주문은 계속됩니다. 마지막으로 받은 메뉴를 기기에 저장해 두고, 주문은 기기 대기열(Outbox)에 쌓았다가 연결되면 순서대로 보냅니다. 주문마다 고유 번호를 붙여 다시 보내도 한 번만 저장됩니다. 음성 주문은 서버가 필요해서, 끊기면 "화면을 눌러 주문해 주세요"로 안내합니다.
Q14
점주가 메뉴나 가격을 바꾸면 바로 반영되나요?
네. 점주 웹에서 저장하면 WebSocket으로 태블릿에 알리고, 30초마다 버전도 확인합니다. 손님이 주문하는 도중이면 그 주문이 끝난 뒤 새 메뉴를 적용하고, 결제 중에 가격이 바뀌었으면 새 가격으로 다시 계산해 알려 줍니다.
Q15
평가는 어떻게 했나요? 100%는 너무 높지 않나요?
저희가 만든 합성 발화 67개로 잰 값이라 범위가 좁습니다. 의도 분류 67개, 품목·수량 41개, 옵션 6개, 상황 추천 15개가 모두 맞았고, 추천은 상위 3개 안에 적합한 메뉴가 있는지로 쟀습니다(상위 3개 중 적합 메뉴 비율은 95.6%). 실제 손님 말투와 마이크 환경은 아직 반영되지 않았습니다.출처: ml/voice_eval/REPORT.md, 2026-11-11 실행
점주·사업
Q16
매장 이익 우선으로 두면 손님한테 손해 아닌가요?
상황에 맞지 않는 메뉴는 이익이 커도 추천하지 않도록 기준선을 뒀습니다. 같은 상황 질의 15개에 정책만 바꿔 보니, 1순위 평균 원가율은 31.6% → 27.1% → 23.5%로 내려가고 추천 적합률은 세 경우 모두 100%였습니다. 맞는 메뉴들 가운데서 이익이 나은 쪽을 앞에 둘 뿐입니다.
Q17
점주는 무엇을 설정하나요?
메뉴판(옵션·필수 선택·품절·노출 순서·사진), AI 추천(상황 태그·동의어·원가율·정책), 음성 설정(사용 여부·안내 속도·추가 제안), 통계, 직원 호출 알림입니다. 통계에서는 음성 주문 비율, 추천 선택률, 추천을 거친 매출, 인기 메뉴를 봅니다.
Q18
AI 사용료가 많이 나오지 않나요?
가장 가벼운 Haiku 모델을 쓰고, 짧은 대답은 기기에서 처리해 호출을 줄였습니다. 주문 한 건당 실제 비용은 아직 재지 않았습니다. 실제 API 키 경로에서 응답 시간과 함께 정리할 예정입니다.
Q19
실제 매장에 바로 쓸 수 있나요?
아직은 시연 단계입니다. 실제 결제 연동, HTTPS를 갖춘 서버 배치, 실기기 마이크 검증, 사용자 테스트가 남았습니다. 지금은 노트북 서버와 같은 Wi-Fi의 태블릿으로 시연합니다.
Q20
직원이 하던 일을 대신하는 건가요?
직원이 하던 추천과 응대를 키오스크 앞에서도 받을 수 있게 하려는 것입니다. 도움이 필요하면 화면의 직원 호출로 점주 웹에 바로 알림이 가도록 했습니다.
접근성·개인정보
Q21
말씀하신 법적 의무가 정확히 뭔가요?
장애인차별금지법 시행령 제10조의2에 따라 키오스크(무인정보단말기)를 두는 사업자는 장애인이 동등하게 이용할 수 있도록 편의를 제공해야 합니다. 별표 2의2가 사업자별 적용 시기를 정하고, 그 전에 설치한 기존 키오스크는 2026년 1월 28일부터 적용됩니다. 소상공인 매장처럼 예외가 인정되는 경우에는 보조 기기·소프트웨어나 보조 인력과 호출벨을 두는 방법도 인정됩니다.출처: 국가법령정보, 장애인차별금지법 시행령(시행 2026.10.2) 제10조의2, 별표 2의2
Q22
그럼 이 키오스크는 그 기준을 통과한 건가요?
아니요, 인증이나 검증을 받은 제품은 아닙니다. 음성 주문, 큰 글씨·느린 음성 모드, 직원 호출처럼 접근성을 높이는 방향으로 만든 캡스톤 프로젝트이고, 고시된 검증기준 항목별로 점검하지는 않았습니다.
Q23
제 말이 외부 AI 회사로 가는 거죠?
목소리 파일은 가지 않고, 인식된 문장 글자가 저희 서버를 거쳐 Claude(Anthropic) API로 갑니다. 저희 서버는 그 문장을 DB나 로그에 남기지 않습니다. 음성을 글자로 바꾸는 단계는 안드로이드 내장 인식기가 하는데, 기기 설정에 따라 처리 방식이 달라서 가능하면 오프라인 한국어 인식 팩을 설치해 씁니다.
Q24
다음 손님이 앞사람 주문을 보게 되진 않나요?
결제가 끝나거나 90초 동안 조작이 없으면 처음 화면으로 돌아가 장바구니와 대화를 비웁니다. 장바구니가 남아 있으면 20초 동안 계속할지 먼저 물어봅니다.
프로젝트
Q25
팀은 어떻게 나눠 만들었나요?
5인 팀이 키오스크 앱, 서버, 점주·회사 관리자 웹, 하드웨어 케이스를 나눠 맡았습니다. 담당 부분에 대한 질문은 그 부분을 만든 팀원이 직접 답합니다.
Q26
처음 계획에서 바뀐 게 있나요?
"말로야" 같은 호출어를 뺐고, 기기 안 AI 대신 서버 AI를 택했습니다. 호출어는 상시 청취가 필요해 오작동과 개인정보 부담이 있어서 버튼으로만 시작하게 했습니다. 바꾼 결정은 모두 이유와 함께 설계 문서에 남겼습니다.
Q27
가장 어려웠던 점은요?
AI가 그럴듯하지만 틀린 답을 할 때를 막는 일이었습니다. 그래서 AI에게는 해석과 적합도만 맡기고, 순위·옵션 확인·장바구니 변경은 규칙과 코드가 하게 나눴고, 담기 전 확인 질문과 서버의 메뉴 대조를 두었습니다. 음성 인식이 메뉴를 다른 낱말로 받아 적는 문제도 발음 비교로 따로 풀었습니다.
Q28
다음에 무엇을 할 건가요?
네 가지입니다. 실제 API 경로에서 응답 시간을 2초 가까이 줄이기, 갤럭시 탭 실기기 마이크와 케이스 검증, 시니어 사용자 테스트(주문 완료율 80% 목표, 터치 대비 탭 수·시간 비교. 앱에 측정 기록 기능이 들어 있음), HTTPS 서버 배치와 실제 결제 연동입니다.
Q29
메뉴 사진은 직접 찍었나요?
시연 메뉴 40개 사진은 Wikimedia Commons의 자유 라이선스 사진입니다. 저작자와 라이선스를 server/menu_image_credits.md에 정리했고, 실제 매장에서는 점주가 점주 웹에서 사진을 올립니다.
Q30
소개 영상의 키오스크가 실제 제품인가요?
영상 속 기기는 설명용 3D 모델이고, 화면은 실제 앱을 찍은 것입니다. 듣는 중 화면의 장바구니 칸은 대화 내용과 맞추려고 빈 장바구니 화면으로 합성했습니다. 실제 케이스는 팀원이 따로 제작합니다.
