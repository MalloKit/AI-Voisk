# 관리자 알림 최초 확인

## 스키마·프로젝트 정책

사용자가 Workbench에서 확인한 device_alert InnoDB 테이블과 기존 컬럼만 사용합니다.
alert_status는 VARCHAR(20) NOT NULL DEFAULT UNREAD이며 ENUM/CHECK 제한과 트리거가 없다는 사용자 확인을 근거로 합니다.
ACKNOWLEDGED는 기존 운영 데이터에서 발견한 값이 아니라 이번 프로젝트의 신규 확인 상태 정책입니다.
현재 실제 Azure 알림은 사용자 확인 기준 0건이며, 검증용 알림을 Azure에 생성하지 않습니다.
알림 생성·해결 담당자는 UNREAD/ACKNOWLEDGED 정책과 최초 기록 보존을 공유해야 합니다.

## PATCH /admin/alerts/{alert_id}/acknowledge

요청은 필수 expected_status: UNREAD 한 필드만 허용합니다. 다른 값·추가 필드는 422입니다.
양의 INT 알림 ID(최대 2147483647)를 사용합니다. 관리자 ID·시각·목표 상태는 클라이언트가 지정하지 않습니다.
기존 로컬 IP 제한·관리자 세션·company_admin 역할·Origin·CSRF·쿠키 정책을 재사용합니다.
관리자는 require_admin(request)의 session.admin.admin_id에서 결정합니다.

UTC 세션 설정 → 트랜잭션 → 알림 단독 행 FOR UPDATE → 상태·기록 검사 →
필요할 때 3개 컬럼 UPDATE → 기존 공개 JOIN 상세·영향 행 수·결과 확인 → COMMIT 순서입니다.
실패하면 ROLLBACK하고 연결을 닫습니다. SQL 값은 바인딩하며 내부 오류·입력을 응답에 반사하지 않습니다.

- UNREAD + 확인 시각/관리자 모두 NULL: ACKNOWLEDGED, DB CURRENT_TIMESTAMP, 세션 관리자 ID 저장.
- ACKNOWLEDGED + 완전한 기록 + 같은 관리자: UPDATE 없이 200, 최초 기록 보존.
- 다른 관리자의 선행 확인, 불완전한 기록, UNREAD와 확인 기록 불일치, 알 수 없는 상태: 409.
- 없는 알림 404, 잘못된 입력 422, 인증 없음/만료 401, 권한/Origin/CSRF 403.
- DB 오류·결과 불명확: 안전한 503. 쓰기 자동 재시도 없음.

성공은 200 + 기존 AdminAlertView 14개 공개 필드입니다. 기존 GET 계약을 변경하지 않습니다.
확인 시각은 DB에서 생성하고 기존 UTC 세션 기반 오프셋 포함 ISO 8601로 반환합니다.
resolved_at·발생 시각·본문·유형·심각도·기기 관계는 수정하지 않습니다.
기기·주문·메뉴·매장 데이터도 변경하지 않습니다. 기기 행을 잠그거나 온라인 상태를 판정하지 않습니다.
확인은 장애 해결이 아닙니다. 기존 resolved_at이 있어도 보존합니다.
전체 확인 이력·확인 취소·장애 해결·알림 생성·삭제는 구현하지 않습니다.

## 관리자 화면

기존 AlertsPage.tsx 내부 실제 상세 컴포넌트를 유지합니다.
실제 UNREAD + 확인 시각/관리자 NULL이며 Repository가 쓰기를 지원할 때만 확인 완료 버튼을 제공합니다.
확인의 의미를 안내하고 명시적인 클릭으로 저장합니다. 저장 중 중복 클릭·모달 닫기·Escape를 차단합니다.
409/404 이후 오래된 상세로 재저장하지 않으며 상세 다시 조회를 제공합니다.
성공 응답은 서버 공개 상세이며, 이후 열린 상세 GET과 공유 alertsResult를 재조회합니다.
목록 필터·검색은 유지됩니다. 대시보드의 정확한 alert_status === UNREAD 집계는 변경하지 않습니다.
주문·매장·점주·기기 목록은 불필요하게 다시 조회하지 않습니다.

저장 성공과 목록/상세 재조회 실패는 별도 메시지로 표시합니다.
재조회 실패를 정상 0건이나 이전 미열람 수로 표시하지 않고 기존 오류·재시도를 사용합니다.
숫자를 임의로 빼거나 Mock 값으로 채우지 않습니다.
Mock 문자열 ID·메모리 확인 함수는 그대로 유지하며 실제 정수 ID PATCH와 결합하지 않습니다.
원본 알림 내용은 React 텍스트로만 표시합니다.

## 격리 검증과 남은 확인

실제 Azure 연결을 차단한 SQLite 메모리 DB 및 Mock HTTP를 사용합니다.
동일 관리자 재요청, 다른 관리자 선행 확인, 오류·롤백, 세션 만료·권한·CSRF, 공개 응답,
해소 기록·기기·주문 보존, UI 중복 방지·필터·목록/상세/대시보드 갱신을 검증합니다.
SQLite의 FOR UPDATE 제거 모형은 실제 MySQL 행 잠금이나 동시 확인 직렬화 검증이 아닙니다.

격리 MySQL 추가 검증: 두 연결의 동시 확인, 동일 관리자 재시도와 다른 관리자 409,
FK·잠금 대기·교착·커밋 실패 및 UTC TIMESTAMP 변환을 확인해야 합니다.
실제 Azure 저장 검증은 별도 승인 후 진행합니다. 운영 알림 0건을 이유로 가짜 알림을 생성하지 않습니다.
