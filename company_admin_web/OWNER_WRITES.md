# 점주 계정 생성 및 매장 연결

회사 관리자 전용 기능입니다. 점주 로그인·점주 세션·비밀번호 초기화·계정 삭제는 구현하지 않습니다.
실제 Azure 데이터/스키마/ERD/엑셀은 변경하지 않았습니다.

## 확인된 스키마와 입력 정책

- 사용자 Workbench 확인: owner_id INT PK AUTO_INCREMENT, own_login_id VARCHAR(100) NOT NULL,
  own_pw VARCHAR(255) NOT NULL. uq_owner_login_id UNIQUE, utf8mb4_0900_ai_ci.
- store.owner_id는 NULL 가능한 owner FK이며 한 점주에 여러 매장을 연결할 수 있습니다.
- 신규 로그인 ID: 소문자 영문·숫자·마침표·밑줄·하이픈, 4~100자. 앞뒤 공백을 포함한 잘못된 ID는 거부합니다.
  기존 ID를 정정하거나 소문자로 바꾸지 않습니다. 기존 혼합 대소문자 ID와 신규 소문자 ID의 충돌은 DB가 최종 판정합니다.
  신규 요청에 대문자를 넣으면 형식 오류 422이며, 형식이 유효한 ID가 기존 값과 충돌하면 409입니다.
- 비밀번호: Unicode 코드 포인트 15~128자. 전체 공백·제어 문자·고립 surrogate는 거부합니다.
  허용한 비밀번호의 앞뒤 공백은 제거하지 않습니다. 확인 값은 UI에서만 검사하고 API에 전송하지 않습니다.
- 정책 위치: src/data/ownerCredentials.ts, server/owner_write_service.py의 상수·OwnerCreate 검증.

## POST /admin/owners

요청 필드는 login_id, password 두 개만 허용합니다. role, admin_id, password_confirm 등 추가 필드는 422입니다.
관리자 로그인 세션, company_admin 역할, 기존 로컬 접근 제한, 허용 Origin과 세션 CSRF가 필요합니다.

성공 201: owner_id, login_id, store_count: 0만 반환합니다. 기존 parseOwner와 목록/상세 GET 계약을 유지합니다.
ID 중복 409, 입력 오류 422, 과도한 본문 413, 인증 없음/만료 401, 권한·Origin·CSRF 오류 403,
DB 오류 또는 저장 결과 불명확 503입니다. DB 오류·검증 오류가 입력 본문·SQL·비밀 정보를 반사하지 않습니다.

기존 admin_auth.hasher(PasswordHasher, argon2-cffi==25.1.0)와 verify_password를 그대로 재사용합니다.
Argon2id v19, 메모리 65536KiB, time_cost 3, parallelism 4, 랜덤 salt 16바이트, hash 32바이트가 현재 생성 정책입니다.
관리자 인증의 기존 검증 허용 정책을 변경하지 않았습니다. 생성 후 기존 검증 함수로 호환성을 확인하고,
인코딩 문자열이 255자 이내일 때만 저장합니다. salt·알고리즘·비용을 포함한 인코딩 문자열 전체를 own_pw에 저장합니다.
원문·해시를 응답·로그·프론트엔드 모델에 넣지 않습니다. 생성 서비스는 저장된 비밀번호를 SELECT하지 않습니다.
해시 생성은 트랜잭션을 열기 전에 수행하고 INSERT·생성 ID·영향 행 수·저장된 공개 필드 확인 후 커밋합니다.
실패하면 롤백합니다. 모든 SQL 값은 바인딩합니다. UNIQUE 최종 방어를 사전 조회로 대체하지 않습니다.

## PATCH /admin/stores/{store_id}/owner

owner_id와 expected_owner_id는 모두 필수입니다. 각각 양의 INT 또는 null을 받으며 문자열·bool·추가 필드는 거부합니다.
owner_id는 목표 점주, expected_owner_id는 관리자가 실제 매장 상세에서 확인한 기존 점주입니다.
null로 설정하면 해제합니다. 기본 정보 PATCH /admin/stores/{id}의 owner_id 금지 정책은 유지합니다.

관리자 세션·역할·Origin·CSRF와 기존 로컬 제한을 적용합니다.
매장 행을 FOR UPDATE로 잠근 뒤 기존 연결과 기대값이 다르면 409입니다. 대상 점주도 존재 확인·행 잠금을 적용합니다.
동일 값이면 UPDATE 없이 성공합니다. 변경 시 store.owner_id만 갱신하고 영향 행 수를 검사합니다.
관리자·대표자·메뉴·주문·기기·다른 매장의 연결은 변경하지 않습니다.
JOIN한 공개 상세를 읽고 커밋하며, 실패하면 롤백합니다. 성공 응답은 기존 AdminStoreView입니다.
없는 매장/점주 404, 동시 변경·FK 충돌 409, 입력 오류 422, 기타 저장 결과 불명확 503입니다.

잠금 순서는 매장 → 대상 점주입니다. 다른 쓰기 서비스와의 교착 상황이 있을 수 있으므로 안전한 실패 응답을 제공하며
자동 쓰기 재시도는 하지 않습니다. 네트워크·커밋 결과가 불명확하면 목록·상세를 확인한 뒤 사용자가 다시 시도해야 합니다.

## 관리자 UI와 갱신

- 점주 계정 생성 모달: 필수값·ID·비밀번호·확인 검증, 표시/숨기기, 고정 하단 등록/취소.
- 매장 상세의 점주 연결 관리: 현재 연결과 ID·로그인 ID 선택 목록, 변경/해제 확인 체크박스.
- 저장 중 입력·중복 제출·취소·Escape·배경 닫기를 차단합니다. 실패 시 성공으로 표시하지 않습니다.
- 404/409 이후에는 오래된 기대값으로 다시 저장하지 않습니다. 취소하면 실제 매장 상세를 새로 조회합니다.
- 생성 후 ownersResult를, 연결 변경 후 storesResult와 ownersResult를 갱신합니다.
  연결 모달 종료 후 상세도 재조회합니다. 주문·기기·알림 목록은 불필요하게 다시 조회하지 않습니다.
- 운영 요약은 같은 storesResult를 사용하므로 미연결 매장 수·목록도 최신화됩니다.
- Mock 계정 생성은 제공하지 않습니다. 실제 매장 + Mock 점주 설정에서는 연결 관리 버튼을 제공하지 않습니다.
  실제 API 실패를 Mock 데이터로 대체하지 않습니다.

## 점주 웹 담당자에게 전달할 계약

해시 정책·UTF-8 처리·ID 규칙을 합의하고, 향후 인증 전용 함수에서만 저장 해시를 검증해야 합니다.
현재 회사 관리자 세션을 점주 인증으로 사용하지 않습니다. 초기 비밀번호는 일회용·강제 변경·자동 만료가 아닙니다.
점주 업무 API는 별도 점주 인증과 매 요청의 store.owner_id 소속 검사가 필요합니다. 이번에 구현하지 않았습니다.
점주 변경 후 과거 주문 열람 정책도 미확정이며 주문 데이터와 접근 권한을 이번 기능에서 변경하지 않았습니다.

## 격리 검증과 남은 검증

SQLite 메모리 DB + 실제 관리자 로그인/CSRF 테스트, Mock HTTP + 실제 Repository 테스트를 사용합니다.
합성 비밀번호를 실행 중 생성하며 실제 Azure DB 연결은 테스트에서 차단합니다.
SQLite NOCASE는 ASCII 대소문자 충돌만 검증합니다. MySQL utf8mb4_0900_ai_ci의 전체 동등성이나 실제 FOR UPDATE,
교착·동시 트랜잭션을 검증한 것으로 취급하지 않습니다.

별도 격리 MySQL에서 추가 확인할 항목:
- uq_owner_login_id와 실제 collation의 대소문자·악센트·공백 비교 및 동시 INSERT 중복 방지.
- 두 연결의 같은 매장 변경 대기 → 기대값 재검사 409, 교착·타임아웃 및 롤백.
- FK·권한·영향 행 수와 커밋 실패 시 처리.
실제 Azure 생성·연결 검증은 별도 승인 후 수행해야 하며 이번에는 실행하지 않았습니다.
