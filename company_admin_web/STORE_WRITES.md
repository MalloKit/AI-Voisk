# 관리자 매장 등록·수정 (2026-10-27)

## 확인된 DB 구조와 범위

사용자가 Azure MySQL Workbench의 `SHOW CREATE TABLE store` 결과로 확인한 스키마를 기준으로 구현했습니다. 이번 Work 구현 중에는 Azure DB 접속·쓰기·DDL을 실행하지 않았습니다. 앞선 읽기 전용 접속 시도는 오류 2003으로 실패했습니다.

| DB 컬럼 | 자료형 | NULL | 입력/관리 정책 |
| --- | --- | --- | --- |
| store_id | INT AUTO_INCREMENT PK | 불가 | DB 생성, 변경 불가 |
| store_nm | VARCHAR(100) | 불가 | 매장명 |
| store_add1 | VARCHAR(200) | 불가 | 주소 |
| store_add2 | VARCHAR(200) | 허용 | 상세 주소, 빈 문자열은 NULL |
| store_code | CHAR(5) | 불가 | **우편번호**. 자동 생성·고유 코드로 사용하지 않음 |
| store_phone | VARCHAR(50) | 불가 | 전화번호 |
| business_no | CHAR(10) | 불가 | 사업자번호 |
| store_owner_nm | VARCHAR(50) | 불가 | 대표자명 |
| store_type | VARCHAR(200) | 불가 | 업종, 임의 ENUM 제한 없음 |
| admin_id | INT FK → admin.admin_id | 불가 | 등록은 서버 세션, 수정은 기존 값 유지 |
| owner_id | INT FK → owner.owner_id | 허용 | 등록은 NULL, 수정은 기존 연결 유지 |

엔진은 InnoDB입니다. **store_code와 business_no에 UNIQUE를 가정하지 않으며 중복 등록·수정을 허용합니다.** 테이블·컬럼·인덱스·제약·엑셀·ERD 변경은 없습니다.

입력 정책은 DB 제약과 구분합니다. 앞뒤 공백을 제거하고 필수 문자열의 공백만 입력, 제어 문자, 길이 초과를 거부합니다. 우편번호는 ASCII 숫자 5자리, 사업자번호는 하이픈 없는 ASCII 숫자 10자리로 입력받습니다. 이는 서버/웹 검증 정책이며 DB에 CHECK를 추가한 것이 아닙니다. 사업자번호의 실재 여부·체크섬·대표자 실명은 검증하지 않습니다. 전화번호는 길이·공백·제어 문자만 검사하며 임의 전화번호 정규식은 강제하지 않습니다.

## API

모든 경로는 기존 로컬 접근 제한, 회사 관리자 역할, 서버 세션, Origin 및 세션 결합 CSRF 검사를 사용합니다. JSON 원문에 admin_id·owner_id·store_id 등 허용하지 않은 키가 있으면 422입니다.

| 요청 | 성공 | 동작 |
| --- | --- | --- |
| POST /admin/stores | 201 + 기존 AdminStoreView | 기본 정보 등록, admin_id는 세션, owner_id는 NULL |
| PATCH /admin/stores/{store_id} | 200 + 기존 AdminStoreView | 제공한 기본 정보 필드만 수정 |
| 기존 GET 목록·상세 | 기존과 동일 | 응답 필드·JSON 형식 유지 |

등록 예시 (모두 테스트용 기본 정보):
```json
{
  "store_name": "시연 매장",
  "store_code": "00123",
  "store_type": "카페",
  "address": "부산",
  "address_detail": null,
  "phone": "051-123-4567",
  "business_no": "0000000001",
  "representative": "대표자"
}
```

`address_detail`만 생략/NULL을 허용합니다. PATCH는 비어 있지 않은 부분 객체이며, 다른 필드에 NULL을 지정하면 422입니다. 상세 주소 해제는 `{"address_detail": null}`입니다. 관리자·점주 연결과 기본키는 변경할 수 없습니다.

오류:
- 401: 비로그인·만료된 세션.
- 403: 다른 역할·로컬 제한·허용하지 않은 Origin·잘못된 CSRF.
- 404: 수정 대상 매장 없음.
- 409: MySQL 중복키/FK 충돌(1062/1451/1452). 현재 우편번호·사업자번호 중복에는 적용하지 않음.
- 422: 누락·형식·길이·알 수 없는 필드·빈 PATCH. 입력 원문이나 내부 오류를 반사하지 않음.
- 503: 연결·SQL·커밋·영향 행 수 등 저장 처리 실패. SQL·접속 정보는 반환하지 않음.

브라우저는 같은 API base의 GET /auth/admin/csrf에서 최신 토큰을 얻은 뒤 X-CSRF-Token 헤더로 POST/PATCH합니다. 쿠키 credentials=include, cache=no-store를 유지합니다. CORS는 기존 정확한 허용 출처·credentials·헤더를 유지하고 PATCH만 추가했습니다. HTTPS/SameSite/HttpOnly/만료·로그아웃 정책은 [AUTH.md](../server/AUTH.md)와 동일합니다.

## 트랜잭션·동시성·재시도

- 명시적인 쓰기 트랜잭션, 고정 SQL 컬럼 목록과 파라미터 바인딩을 사용합니다.
- 등록은 INSERT 1행과 생성 ID를 검증합니다.
- 수정은 SELECT ... FOR UPDATE로 대상 및 현재 관계를 조회한 후 변경된 기본 정보만 UPDATE합니다. 수정 시 담당 관리자와 점주 ID를 대입하지 않습니다.
- 변경이 실제로 있으면 영향 행 수가 1이어야 합니다. 같은 값인 PATCH는 UPDATE 없이 정상 상세를 반환합니다.
- 저장 상세를 같은 트랜잭션에서 읽은 뒤 commit합니다. 예외는 rollback, 항상 연결을 종료합니다.
- 잠금으로 요청 중 일관성을 유지하지만 사용자가 폼을 연 뒤 다른 사용자가 같은 필드를 수정한 경우를 탐지하는 버전/ETag는 없습니다. 같은 필드에 대한 나중 저장이 우선합니다. 변경하지 않은 필드는 웹 PATCH에서 보내지 않습니다.
- 쓰기 자동 재시도·멱등키는 없습니다. 서버가 commit했지만 응답이 유실될 수 있으므로 네트워크/503 오류는 **저장 여부 미확인**으로 안내합니다. 특히 등록은 목록을 새로고침해 확인한 뒤 다시 제출해야 합니다. 브라우저 AbortSignal은 서버의 commit 취소를 보장하지 않습니다.
- 프론트엔드는 저장 중 버튼·입력·모달 닫기/Escape/배경 클릭을 잠그고 동기 ref로 중복 submit을 차단합니다. 별도 브라우저의 중복 등록까지 차단하는 기능은 아닙니다.

## UI 및 공유 상태

- 실제 매장 관리에서 등록 버튼, 실제 상세 조회 성공 후 수정 버튼을 표시합니다.
- 기존 공통 Modal·field·버튼·디자인 토큰을 사용합니다. PC는 2열, 599px 이하는 1열입니다.
- 필수값·길이·우편번호/사업자번호 형식 오류를 항목별로 표시하고 첫 오류로 포커스를 이동합니다.
- 취소·Escape·닫기 후 기존 공통 포커스 복귀를 유지합니다. 폼 안내 문구가 입력란 이름에 포함되지 않도록 aria-labelledby로 구분합니다.
- 성공은 서버가 반환한 매장을 기준으로 표시하고 상세를 다시 조회합니다. App의 기존 storesResult.reload를 호출해 전체 목록·대시보드 등록 매장/미연결 매장 수를 함께 갱신합니다. 새 전역 상태나 별도 목록 캐시를 만들지 않습니다.
- 검색·필터는 저장 전 상태를 유지합니다. 새 데이터가 현재 조건에 맞지 않으면 목록에 보이지 않을 수 있으며 상세에서 저장 결과를 확인할 수 있습니다.
- 저장 성공 후 목록 조회만 실패하면 저장 성공과 조회 실패를 각각 표시합니다. 쓰기를 자동으로 재실행하지 않습니다.
- 401은 기존 세션 만료 이벤트로 로그인 화면 이동·App 해제·공유 조회 상태 초기화를 수행합니다. 폼이 해제되면 요청을 abort합니다.
- 명시적 Mock 매장 모드는 기존 조회·검색·상세를 유지하며 실제 DB 저장 버튼은 표시하지 않습니다. API 오류에 따른 Mock 대체는 없습니다.
- 점주 연결, 삭제, 관리자 변경, 계정 생성, 기기 이동, 메뉴 수정은 추가하지 않았습니다.

## 검증과 실제 Azure 검증 절차

검증은 Mock HTTP, 격리된 SQLite 메모리 DB 및 실제 브라우저와 격리 서버로 수행합니다. SQLite 어댑터는 MySQL 바인딩/트랜잭션 구문을 변환하므로 InnoDB 잠금·collation·실제 권한·네트워크·커밋 유실까지 검증한 것은 아닙니다.

- 웹: npm test / npm run build
- 서버: python -m unittest discover -p "test_*.py" -v
- 계약: node --experimental-transform-types --test scripts/store-contract.test.mjs scripts/verify-owner-contract.mjs scripts/verify-device-contract.mjs scripts/verify-alert-contract.mjs

기존 GET 계약과 주문 UUID 재시도·기기 활성화 규칙, 로그인·로그아웃·만료, 6개 화면 회귀 테스트는 유지합니다. 기존 'POST 미지원' 테스트만 등록 기능에 맞춰 '빈 등록 422, PUT/DELETE 미지원'으로 변경했습니다. 우편번호의 의미가 확정됨에 따라 기존 상세 라벨 테스트는 '의미 미확인'에서 실제 우편번호 라벨과 원문 보존 검증으로 갱신했습니다.

### 별도 승인 후에만 실행할 실제 DB 검증
1. 팀과 검증 대상 매장, 입력값, 허용할 등록/수정 범위를 합의하고 쓰기 승인을 받습니다. 승인 전에는 버튼으로 실제 저장하지 않습니다.
2. 동일 커밋의 서버/웹으로 로그인하고 기존 조회를 먼저 확인합니다. DB 계정의 필요한 SELECT/INSERT/UPDATE 권한은 팀과 확인하되 이번 작업에서 권한 변경을 실행하지 않습니다.
3. 승인된 입력으로 한 건만 등록하고 응답 ID, admin_id(세션), owner_id(NULL), NULL 상세 주소, 선행 0, 목록·대시보드 갱신을 확인합니다.
4. 승인된 매장의 기본 정보만 수정하고 store_id/admin_id/owner_id 및 기존 주문·기기 연결이 유지되는지 읽기 조회로 확인합니다.
5. 중복 우편번호·사업자번호 테스트가 필요하면 별도 승인된 등록 건으로만 검사합니다. 운영 데이터로 임의 충돌·실패를 유발하지 않습니다.
6. MySQL 문자 길이·트랜잭션/잠금 동작, 실제 CORS PATCH와 CSRF·만료 후 차단, 저장 후 재로그인 조회를 확인합니다. 오류 시 저장 여부부터 조회합니다.
7. 자동 삭제/복구 SQL은 실행하지 않습니다. 테스트 데이터 정리나 기존 값 복원이 필요하면 별도 승인 및 기록 후 수행합니다.
