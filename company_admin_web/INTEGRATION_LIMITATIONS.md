# 조회 일관성과 전시 편집 운영 제한

## 주문 목록 조회

- 기존 GET /admin/orders의 LIMIT/OFFSET 계약을 유지합니다.
- order_id가 여러 페이지에 나타나면 첫 번째 응답만 유지하며 처음 받은 순서를 보존합니다. 대시보드와 주문 조회는 이 동일한 중복 제거 결과를 공유합니다.
- 다음 offset은 중복 제거 전 실제 수신 행 수로 증가합니다. 고유 주문 수를 offset으로 사용하지 않습니다.
- 한 번의 조회는 첫 응답의 total을 진행 기준으로 사용하고 빈 페이지에서는 종료합니다. 이후 total이 증가해도 새 주문을 끝없이 따라가지 않습니다. 뒤 페이지가 실패하면 부분 결과를 정상 목록으로 반환하지 않습니다.
- 첫 total은 DB 스냅샷이나 마지막 주문 ID가 아닙니다. 조회 중 삽입·삭제·정렬 변화가 있으면 최신 주문 또는 일부 주문의 누락과 페이지 간 시점 차이는 여전히 가능합니다. 중복 제거는 정확한 동일 시점 조회를 보장하지 않습니다. 새로고침으로 다시 조회합니다.
- 엄격한 동일 시점 조회가 필요하면 이후 별도 작업에서 고정 조회 기준이나 커서 방식에 대해 서버 담당자와 합의해야 합니다. 이번 작업은 새 API나 주문 생성·UUID 재시도 변경을 포함하지 않습니다.

## 매장 기본 정보의 동시 수정

- 현재 기본 정보 PATCH는 행 잠금을 사용하지만 화면에서 읽은 이전 값과 비교하지 않습니다. 오래된 화면에서 같은 필드를 나중에 저장하면 앞선 변경을 덮어쓸 수 있습니다.
- 전시에서는 단일 관리자 편집 운영을 전제로 합니다. 같은 관리자 계정이라도 여러 탭·브라우저·PC에서 같은 매장을 동시에 편집하지 않습니다. 편집 시작 전 최신 상세를 조회하고 다른 편집을 닫습니다.
- 저장 결과가 불명확하면 재저장하기 전에 목록·상세에서 실제 저장 여부를 확인합니다.
- 이 운영 규칙은 서버의 동시 수정 방지 기능이 아닙니다. 기존 PATCH 계약·DB 스키마를 유지하며 ETag·버전 컬럼·기존 값 비교는 추가하지 않았습니다.
- 점주 연결과 기기 상태의 기존 expected 값 검사, 알림 최초 확인 충돌 정책은 그대로 유지합니다.

실제 Azure MySQL의 데이터·스키마는 이번 작업에서 변경하지 않습니다.
